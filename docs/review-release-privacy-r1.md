## Deployment review and remaining release gates

- **High / conditional gate — effective shared Caddy log privacy.** `deploy/Caddyfile.production` is a site fragment, not a complete privacy configuration. `docs/deployment.md:51` correctly requires the existing global logger to remove request URI/headers, both client/remote IP fields and remote port, with no site access log. `deploy/Caddyfile.local` demonstrates these filters; `scripts/test-caddy-logs.sh` tests only that local file. The lead must verify the actual shared configuration and a synthetic upstream failure before accepting public traffic. Source review cannot certify it.
- **High / conditional gate — exact live proxy peer.** `config.go:89` accepts only individual addresses or host prefixes; `security.go:102` trusts one forwarded address only from a configured peer. The production Caddy fragment overwrites X-Forwarded-For and removes alternate forwarded headers. Verify the actual peer in the app's ingress network, host-only trust, no stale placeholder, and an IP-stability/update plan. Verify shared Caddy inbound timeouts/header limits as required by the runbook; the production fragment alone supplies only body and upstream limits.
- **Pass, source inspection — Host/Origin/CSRF and private data boundary.** Production fixes HTTPS origin and disables development. `server.go:123` checks Host and exact Origin for mutations; admin authorization additionally validates one CSRF header against the server session. Production cookies are Secure, HttpOnly, SameSite=Strict and host-prefixed. Public list/search selects approved features and safe fields only; details/context/admin notes stay in authorized endpoints. Context URLs lose query/userinfo/fragment and unsafe paths. The theme change persists only the appearance preference.
- **Pass, source inspection — isolation, credentials and resource bounds.** Production publishes no app or DB host ports; DB uses only an internal network. App mounts only its three secret files, read-only, runs non-root with a read-only filesystem and dropped capabilities. Init creates a restricted application DB role; generated credentials are not passed in application arguments. Protected parent directories make the documented readable bind-mounted files viable. App/DB memory, CPU, process and log-rotation limits are explicit; request/body/concurrency/DB-time and lifetime storage budgets exist. Verify host capacity and actual production directory permissions; source budgets are not a load test.
- **Pass with operational follow-through — initialization and backups.** `init-env.sh` preserves existing secrets, so generate fresh production credentials in a clean destination rather than copying local state. `backup.sh` checks the effective target through the application parser, writes a unique mode-0600 staging file, validates the dump listing and publishes atomically. The runbook covers separate-DB restore, secret-file inode changes, app recreation and protected independent backup storage. A listing check is not a restore test; retain live restore/retention/offsite evidence separately. Avoid printing init SQL/error details or configuration while operating credentials.

Not inspected: the live host, effective proxy/database log settings, DNS, GitHub visibility/access settings, actual built-image contents or registries, unreachable/reflog-only Git objects, remote-only refs, and ignored report/dump bodies. No deployment approval is inferred from historical review notes. Re-scan new commits or generated release records containing operational evidence before pushing them.
