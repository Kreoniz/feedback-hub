# Архитектура и решения

Дата: 2026-10-21. Решения для текущего MVP, не обещание deployed-состояния.

## Границы

Один Go-процесс, одна PostgreSQL, собранная React SPA. Caddy завершает TLS и проксирует на закрытый порт. Отдельного frontend runtime, Redis, очереди, ORM и клиентского state manager нет. SQL-миграции встроены в бинарник и применяются до обслуживания запросов под блокировкой. Начальная поддержка — одна app replica, поскольку быстрые rate-limit gates находятся в памяти. Масштабирование потребует общих лимитов.

Публичная доска читает только одобренные feature requests. SQL/API projection не содержит приватных полей; frontend не получает их скрытыми свойствами. Bug reports не имеют публичного чтения. Анонимная отправка возвращает непрозрачную квитанцию, по которой нельзя прочитать обращение. Никаких персональных аккаунтов или контактных полей.

## Модель

Небольшой серверный каталог проектов содержит публичные slug/name/description/url; SQL CHECK ограничивает допустимые slug. Отдельной таблицы управления проектами в MVP нет. Обращение связано с проектом и типом feature/bug. Статус выполнения, модерация, приоритет и информативность — отдельные измерения. Новое обращение не получает повышенный приоритет за длину/слова/подробность. Технический контекст — необязательные минимизированные строки. Полезность классифицируется описательно, а важность назначает человек.

Дубликаты сохраняются; администратор связывает только обращения одного проекта/типа. Самоссылки и циклы запрещены. Скрытый дубликат не перетаскивает голоса к другой идее автоматически. Спам помечается модерацией; мат, короткий текст или язык сами по себе не основание для блокировки.

## Идентификация и защита

Подписанная случайная visitor-cookie — средство ограничения повторов, не пользователь и не доступ к приватным данным. Проверка временного токена и honeypot создают небольшое препятствие автоматизации. SQL-ограничения и транзакции защищают от конкурентных повторов и голосов. Сетевые HMAC-идентификаторы ограничивают простую смену cookie; сырой IP не сохраняется. Распределённая атака остаётся отдельной угрозой.

Владелец входит по одному длинному паролю. Bcrypt hash читается из secret-файла. В БД сохраняется hash случайного session-token; cookie — host-only, HttpOnly, SameSite Strict, Secure в production. Origin проверяется на сервере, admin mutations дополнительно требуют CSRF-token. OIDC/passkeys можно добавить позже, когда появится существующий надёжный identity provider; отдельный OAuth-провайдер ради одного владельца увеличил бы объём настройки.

Caddy перезаписывает X-Forwarded-For единственным remote IP. Go доверяет ему только от точного проверенного Caddy IP (/32 или /128), а не от всех приватных диапазонов. За внешним anti-DDoS edge этот контракт потребуется явно изменить: trust CIDR edge и строгий разбор цепочки относятся к будущему ingress-изменению, которое нельзя просто включить переменной приложения.

## Эксплуатация

Секреты вне Git; разные пароли PostgreSQL superuser и ограниченной app-role. App-role без superuser/createdb/createrole, владеет только своей БД для встроенных миграций. Нет опубликованного DB-порта, контейнер приложения read-only/non-root, bounded resources/log rotation. Производственная сеть и точный Caddy hop проверяются до запуска.

Report content автоматически не удаляется: это продуктовые данные. Оператор должен следить за размером БД, создавать защищённые резервные копии и определить срок архивирования перед публичным запуском. Служебные записи имеют ограниченный срок хранения (см. backend README). Backups восстанавливаются сначала в отдельную БД; обновление не удаляет volume.

Уведомления и GitHub Issues отсутствуют. При их добавлении атомарная запись outbox в транзакции с обращением обеспечит повторяемость доставки; сейчас преждевременная очередь не реализуется.
